# AI Agent Workflows 仕様書

## 概要

AIエージェント、Coreモジュール、およびTools群を組み合わせて、一連のタスクやビジネスロジックを実行するためのスクリプト群を配置するディレクトリです。エージェントが主体となって業務プロセスを完遂するためのフロー定義が含まれます。

## 目的

1. エージェントやツールの単体操作だけでなく、それらを数珠つなぎにした「複合的なタスクプロセス（ワークフロー）」を定義する。
2. AIエージェントを利用した自動化スクリプトの実行手順をコードとして明文化し、結果の再現性を確保する。
3. エージェントの動作検証や、今後のバッチ処理基盤への拡張を容易にする。

## 実装の鉄則（Six Strict Rules）

当ディレクトリ内のワークフローは、APIコストの浪費やデータ不整合を防ぐため、以下の **「6つの厳格な鉄則」** に従って実装されなければなりません。

### 1. Thin Orchestrator (ビジネスロジックの禁止)

- ワークフローは「読み込み」「エージェント/ツールの呼び出し」「保存」を繋ぐ単なる **土管（Plumbing）** であること。
- 複雑なデータパース、文字列操作、ドメイン固有の判定ロジックは絶対にワークフロー内に記述せず、`src/domain` や `src/tools` に切り離す。

### 2. Mandatory State Management (強制的な状態管理とチェックポイント)

- 複数ステップにまたがる処理の進捗管理は、必ず `TaskStateManager` 等の専用モジュールを通して行う。開発者独自のアドホックな状態管理（`fs.writeFileSync` での一時フラグ管理など）は禁止する。
- **トランザクション境界（Chunk-based Checkpointing）**: 状態の保存は「論理的なトランザクションの境界（例：1つのエンティティ処理の完了時、または100件のバルク処理の完了バックバッチ）」で行うこと。

### 3. Strict Idempotency (完全な冪等性と再開性の担保)

- いつのタイミングでプロセスが強制終了（OOMやAPIエラー）しても、再実行時に「成功済みのステップを安全にスキップ（再開）」できなければならない。
- 状態を確認せずに外部APIや書き込み処理を実行してはならない。

### 4. File Bucket Relay Compliance & Validate-First (I/Oディレクトリ厳守と事前パース)

- ワークフローの入力元と出力先は、アーキテクチャで定められたバケツリレーのパスを厳守する。標準入出力や揮発的なメモリでのみ状態を受け渡すことは避ける。
- **事前検証 (Validate-First)**: ファイルを受け取る際、直後に必ず Zod スキーマで構造をパース（検証）し、不正なデータであればAPI呼び出し前に直ちに **Fail-Fast** すること。水際でのAPIコスト浪費を防ぐ。

### 5. Fail-Fast & Observability (エラーの隠蔽禁止と可観測性)

- 予期せぬエラーやリトライ上限到達時は、例外を握りつぶさず適切にスタックトレースを残して `exit code 1` 等で即座に異常終了させる。
- **可観測性の確保**: 異常終了させる直前には、`consola.error` 等を用いて「現在処理中だったエンティティの識別子（IDやファイルパスなど）」を必ず標準出力に残し、リカバリを容易にすること。

### 6. Mandatory Dry-run (空走モードの実装義務)

- 破壊的変更（DBへのUpsertやAPIコストの発生）を伴うワークフローは、必ず `--dry-run` フラグの入力をサポートすること。
- 実行対象の件数や事前パース結果のみを事前に（コストゼロかつ安全に）確認できる状態を維持する。
