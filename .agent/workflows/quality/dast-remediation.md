---

このワークフローは、DAST（Dynamic Application Security Testing）ツール OWASP ZAP によって検出された脆弱性レポートに対し、アプリケーションの品質とセキュリティを維持しながら修正を行うための手順です。

場当たり的な対応（単なるフラグ付与や広範な警告無視）を避け、アーキテクチャの妥当性と長期的な保守性を重視します。

# 1. レポートの解析と優先順位付け

1. `gh issue list --label DAST` 等を実行し、最新の DAST Scan Report を取得する。
2. レポート内の **Alert ID**, **Vulnerability Name**, **Risk Level**, **Parameter**, **Evidence** を精査する。
3. 検出された現象が「システムの意図した挙動」か、改善すべき「脆弱性」かを判断する。
4. **【重要】認証コンテキストの確認**: 該当エンドポイントやCookieが「認証済みユーザー専用（Authenticated）」か「パブリックルート（Unauthenticated）」かを必ず確認する。（例：Supabaseのセッションクッキーとロケールクッキーでは同じ警告でも実害が大きく異なるため、この文脈を強制的に意識してトリアージを行う）

# 2. 恒久的・根源的な対応方針 (Root Cause Fix)

安易に `proxy.ts` 等のミドルウェアでヘッダーを上書きせず、以下の優先順位で対策を検討する。

1. **ライブラリ・フレームワーク設定の最適化**:
   - 例: `next-intl` の `localeCookie` 設定など、原因となっているコンポーネント自体の設定で解決できないか検討する。
2. **マジックストリングの排除と適切な環境判定**:
   - 環境判定には必ず `@/lib/constants` の `APP_ENV` または標準の `NODE_ENV` を使用する（VercelのPreview環境も `NODE_ENV=production` になるため、セキュア通信の判定目的であればこれで十分である）。
   - `VERCEL_ENV` は、「Preview環境とProduction環境で明確にシステムの挙動を分ける要件」がある場合のみ評価し、意味のない条件分岐を義務化（技術的負債化）させない。
3. **ミドルウェアでの統合管理**:
   - 重複するヘッダー発行を避け、レスポンス全体に対して一貫性のあるポリシー（CSPなど）を適用する。

# 3. 健全なスキャン抑制 (Secure Filtering)

機能上どうしても警告を解消できない場合、以下のルールに従って抑制を行う。

- **原則: グローバル IGNORE の禁止**:
  - `.zap/zap-rules.conf` で Alert ID 全体を `IGNORE` (非表示) にするのは極力避ける。
  - これは、特定の安全な要素（例: `NEXT_LOCALE`）を隠すついでに、本来保護すべき重要な要素（例: `authjs.session-token`）の脆弱性も見逃すリスクがあるため。
- **第一選択: ZAPネイティブの Alert Filter と構成管理 (Configuration as Code) (推奨)**:
  - ZAPエンジン自身に直接 False Positive として処理させるため、ZAPの Alert Filter 機能を利用する。
  - 設定箇所が分散することを防ぐため、除外設定は必ず **`.context` ファイル等の単一の設定ファイル（Configuration as Code）** を更新する標準手順とし、起動時のコマンド引数による複雑な上書きは避けること。
  - **【重要】除外理由の文書化（Traceability）**: フィルターを設定する際は、その設定ファイル内に「特定のAlert IDと特定のパラメータを**なぜ除外したのか**」という背景情報・理由を必ずコメント（例: XMLファイルの場合は `<!-- NEXT_LOCALE is required for client-side routing -->` など、ファイル形式に合わせた適切な構文）として残すか、リポジトリ内のセキュリティ管理ドキュメントに明記し、将来の監査リスクとなる技術的負債化を防止する。
- **最終手段（フォールバック）: CI/CDでのカスタムパース**:
  - ZAP標準の Alert Filter でどうしても表現できない複雑な条件に直面した場合の最終手段として、`.github/workflows/...` 内のJSONパーススクリプト等で除外を行う。除外ルール増加によるメンテナンスコストの増大に留意すること。

# 4. 検証とフィードバック

1. **静的解析**: `pnpm lint` / `pnpm tsc` を実行。
2. **ビルド検証**: `pnpm build` を実行し、ミドルウェアの変更がルーティングや静的生成に影響しないか確認。
3. **動的検証 (Browser / Environment Parity)**:
   - ローカル（`pnpm dev`）での基本動作確認（Cookieやヘッダーの期待挙動、言語切り替えなどのユーザー動線が正常に機能し続けるか）を実施する。
   - **【重要】** Pull Request 作成後、自動生成される **Vercel Preview URL** に対してブラウザや検証ツールでアクセスし、本番同等のHTTPS環境（およびVercel特有のキャッシュ・ルーティング機構）下において Cookie（`Secure`フラグ等）やヘッダーが正しく付与・動作していることを**最終確認**する。
4. **回顧**:
   - 新しいフィルタリングパターンを導入した場合は、`/retrospective` を通じてこのワークフロー自体を更新し、知見を汎用化する。
