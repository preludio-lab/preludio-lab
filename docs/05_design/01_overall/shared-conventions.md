# Shared Logic Conventions

本ドキュメントでは、プロジェクト内における「横断的関心事（Cross-cutting Concerns）」の配置場所である `src/shared` ディレクトリの役割と、その使用ルールについて定義します。

## 1. 概要と背景

プロジェクト全体から参照されるが、特定のビジネスドメイン（`src/domain`）に属さない機能（i18n、ロギング、エラーハンドリング等）を `src/shared` に集約します。これにより、以下のメリットを享受します。

- **依存の適正化**: Domain層がInfrastructure層に依存するような不自然な関係を解消。
- **カプセル化**: 共通機能の「家」を明確にすることで、トップレベルディレクトリの肥大化を防止。
- **一貫性**: 開発者が「どこに共通機能があるか」を迷わずに済む。

## 2. `src/shared` の構成

### 2.1. 命名の意図

`common` ではなく `shared` を採用しています。

- `common` は「便利な道具箱（Utils）」というニュアンスが強い。
- `shared` は「複数の異なるコンテキスト（Domain, UI, Infra）で共有される重要なコア」という意図を表します。

### 2.2. 現在の構成要素

- **i18n**: `src/shared/i18n` (メッセージファイル、ルーティング設定、コンフィグ)
- **ID**: `src/shared/id.ts` (一意な識別子生成・検証)
- **Validation**: `src/shared/validation`

## 3. 今後の拡張指針

以下の機能についても、順次 `src/shared` への集約を検討します。

- **Logging**: 全レイヤーから使用する共通ロガー。
- **Errors**: プロジェクト全体で共有する標準例外クラスの定義。
- **Types**: プロジェクトの基礎となる共通型定義。

## 4. 使用ルール

1. **ドメイン中立性**: `src/shared` 配下のコードは、特定のドメイン（例: `article`, `composer`）の知識を持ってはいけません。
2. **依存方向**: 全てのレイヤー（Domain, Application, Infrastructure, UI）から参照可能ですが、逆にこれらのレイヤーへの依存を最小限に抑える必要があります。
3. **カプセル化**: 外部に公開するインターフェースは明確にし、内部の実装詳細は隠蔽します。
