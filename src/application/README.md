# アプリケーション層 (src/application)

アプリケーション層は、ドメインモデルを用いて具体的なユースケース（システムが提供する機能）を実現します。
UIや外部APIなどの入出力を受け取り、ドメイン層のビジネスルールをオーケストレーションし、インフラストラクチャ層を用いてデータの永続化を行います。

## 役割

- **ユースケースの実現**: アプリケーション固有のシナリオを単一のクラス・メソッド単位で実装します。
- **トランザクション管理**: 永続化ストレージに対する処理を適切にトランザクショナルに保ちます。
- **ビジネスルールのオーケストレーション**: UI技術（HTTPなど）に依存せず、アクション層から渡された型・構造が検証済みのデータ（Command）を受け取ります。
- **ドメインルールに基づく検証と変換**: 重複チェックなどのビジネスルールに基づく検証を行い、エンティティなど内部で安全に扱える構造に変換します。
- **出力データの成形**: 外部へ返すデータを、内部の複雑なドメインモデルから用途に合わせたシンプルなデータ構造（DTO）に変換して出力します。

## ディレクトリ構成と役割

アプリケーション層内の各ドメインディレクトリ（例:`article/`, `composer/`）は、以下の共通方針に従い責務ごとに分割して構成します。

| 要素        | 命名規則       | 役割と特徴                                                                         |
| :---------- | :------------- | :--------------------------------------------------------------------------------- |
| **UseCase** | `*.usecase.ts` | アプリケーションのビジネスルール（シナリオ）実装。                                 |
| **Command** | `*.command.ts` | 更新系（Create, Update）や特定アクション時の入力データ定義。                       |
| **DTO**     | `*.dto.ts`     | 参照系（Query）などの結果としてクエリ元（UI等）へ返す出力データ定義。              |
| **Master**  | `*.schema.ts`  | マスターデータ（JSONファイル等）として静的に管理・出力されるデータのスキーマ定義。 |

### 1. `usecase/` (Application Business Rules)

ユースケースの実装には、1ファイルにつき単一の責任を持つよう設計します。

- **更新系 (Command: Create/Update/Delete等)**
  - `command` オブジェクトを入力とし、`TransactionManager` を用いて永続化フェーズの整合性を担保します。
  - 作成完了時などのステート変化は、`Logger` を通して運用時の調査・分析（トラッキング）に役立つ構造化ログとして出力します。
  - 検証エラー（重複、競合など）は `AppError` インスタンスとして適切にスロー（例: `'CONFLICT'` 等のコードを付与）し、上位層のエラーハンドラーへ委ねます。
- **参照系 (Query: Get/List/Search等)**
  - リポジトリを介してデータを取得し、後述する `dto` のZodスキーマを通してパース（バリデーション＆フィルタリング）して呼び出し元へ返します。

### 2. `command/` (Input Data)

データの作成や更新に必要な入力フィールドと、そのバリデーション定義です。

- Domain層が持つ純粋なメタデータ定義（`MetadataSchema`等）をベースとし、それぞれのユースケースにおける具体的な入出力要件（例えば「作成時は `slug` フィールドが必須になる」など）に合わせてZodの `extend` を用いて再定義します。
- **[重要] 共通のバリューオブジェクトのバリデーションには直接 `z.string()` 等を使用せず、必ずドメイン層で定義された共通スキーマ（例: `src/domain/shared/common.metadata.ts` の `SlugSchema` など）を利用してください。** これによりシステム全体での仕様（文字数や正規表現）の統一を担保します。
- `z.infer<...>` で型情報を抽出し、ユースケースへの入力引数として利用します。

### 3. `dto/` (Data Transfer Object)

外部インターフェース（APIレスポンス等）へ出力するデータの形式要求、または外部から受け取る入力パラメータの形式要求です。

- **ユースケース駆動のファイル分割と命名 (SRP/ISP)**
  - 巨大な単一ファイルを廃止し、ユースケースごとにファイルを分割します。
  - **UI語彙の排除**: `list` や `detail` などのUI（画面）を連想させる命名は極力避け、`get-composers.dto.ts`（一覧相当）や `get-composer.dto.ts`（単一リソース相当）のように、ユースケース（振る舞い）に基づいた命名を採用してください。
- **Response DTOとRequest DTOの整備**
  - 出力データとしての **Response DTO** (`*.dto.ts`) だけでなく、検索クエリやページネーション、複雑なパラメータを伴うユースケースでは **Request DTO** (`*.request.dto.ts` または同ファイル内のSchema) も整備し、UseCaseの入り口と出口でZodによる防御を確立します。
  - **ZodをSSOTとしたスキーマ駆動と厳密な検証 (Pragmatic Clean Architecture)**
  - TypeScriptの `interface` を手動定義するのではなく、ドメイン層のマスター・スキーマ（例: `ComposerMasterSchema`）をベース（SSOT）として構成します。
  - **派生ルールの徹底**: 「ドメインスキーマはDTOスキーマを知らない（依存の方向は常に DTO → ドメイン）」というルールを徹底します。UIの都合で大元のドメインスキーマを変更するのではなく、DTO層でZodの `.pick()`, `.omit()`, `.extend()` を用いてスキーマを派生させます。
  - **複数ドメインの合成**: `relatedWorks` のように他ドメインのデータを含む場合は、単一のドメインスキーマに無理に `.extend()` するのではなく、複数のドメインスキーマを合成（Composition）するアプローチを取ります。
  - **直列化の責務**: DTOは「型定義」と同時に「直列化の契約」を担います。Date型からString(ISO8601)への変換など、型の不一致が生じる場合はZodの `.transform()` を活用し、マッピング時に自動フォーマット変換が行われる仕組みを構築します。
  - **情報の漏洩防止**: `pick` や `extend` によるスキーマ合成時に意図せず秘匿データや不要なメタデータが混入することを防ぐため、Zodの `strict()` を活用し、自動テストによって定義されたプロパティと一致するかを検証して安全性を担保します。
  - **バリデーションの実行境界**: DTOのランタイムパース（`z.parse()` または `z.safeParse()`）は、原則として「UI層からUseCaseへ入る境界」および「UseCaseからUI層へ出る境界」で実行します。

### 4. `master/` (Master Data Definition)

静的なシステムデータ（マスタ）として管理、あるいはファイルストレージに永続化されるデータのスキーマ定義です。

- **Domain層のスキーマ** と、システムに管理上必要なメタデータ（例: `_schemaVersion` バージョン情報など）を `merge` して構成します。
- **[重要]** 入力用の `command` スキーマに依存（extend等）させず、純粋なドメインモデル（Domain層）を起点（ベース）とするよう設計してください。これにより、永続化層の設計がUIの都合（Command）に引きずられることによる意図せぬ結合を防ぎ、独立性を保つことができます。

## `src/actions` (Server Actions) との棲み分け・境界

Next.js (App Router) において、UIからの入力を直接受け取る Server Actions (`src/actions`) と、本アプリケーション層 (`src/application`) は明確に責務が分かれています。

### 1. `src/actions/` (UI層 / Interface Adapter)

Next.js や HTTP リクエストといった **UIの技術詳細に依存する層** です。

- **リクエストの解釈と型バリデーション**: FormData や JSON 文字列のパース、セッション情報の取得を行い、Zod等を用いて「期待するデータ構造を満たしているか」の表面的なバリデーションを行います。
- **ユースケースの呼び出し**: 検証済みの純粋な TypeScript オブジェクトを `Command` として組み立て、アプリケーション層(UseCase)に渡します。
- **レスポンスの変換**: UseCase が返す結果やスローする `AppError` をキャッチし、フロントエンドが解釈できる汎用フォーマット（例: `ActionResponse`）に変換して返戻します。

### 2. `src/application/` (アプリケーション層)

UIの技術詳細（HTTPヘッダーやFormData等）には **一切依存しない純粋なドメイン機能** の提供に専念します。

- **型の保証は完了済みの前提**: `src/actions` で入力の構造や型（Zodのスキーマチェック等）は保証された上で、クリーンな `Command` データを受け取ります。
- **ビジネスルールの検証**: 例えば「既に同じ Slug が存在しないか」等の、データベースやドメインロジックを伴う奥深い検証・エラー（`AppError`）送出を担当します。
- **オーケストレーションの完遂**: トランザクション制御を通じ、インフラとドメインを連携させ、更新や取得のプロセスを完結させます。

つまり、**フォームの入力形式の違いやHTTPリクエスト等の検証は Action 層** で吸収し、**業務要件に基づくドメイン機能の検証・実行は Application 層** が専任する、という切り分けになります。
